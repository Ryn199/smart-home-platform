SMART HOME IoT BACKEND - IMPLEMENTATION PLAN
===========================================================

PROJECT GOAL
------------

Build a clean, maintainable Smart Home backend for a system consisting of:

- 2 houses initially
- Less than 10 ESP devices initially
- Multiple rooms
- ESP32 devices communicating through MQTT
- Continuous sensor telemetry such as temperature and humidity
- Separate Web Admin frontend
- Flutter mobile application consuming REST API
- Real-time dashboard updates
- Device configuration and control
- Future possibility to grow beyond the initial 2 houses

IMPORTANT:
This project is intentionally NOT over-engineered.

Do not introduce Redis, Kafka, RabbitMQ, TimescaleDB, microservices, Kubernetes,
or other infrastructure unless there is a concrete requirement later.

The architecture must be simple enough for the current scale while remaining
clean enough to evolve later.

===========================================================
4. DEVELOPMENT PRINCIPLES
===========================================================

Follow these rules throughout the implementation:

1. Prefer simple solutions.
2. Do not over-engineer.
3. Keep responsibilities separated.
4. Use TypeScript strictly.
5. Validate all external input.
6. Never trust MQTT payloads blindly.
7. Never expose database credentials to frontend applications.
8. Never let Flutter or Web Admin communicate directly with PostgreSQL.
9. Keep MQTT broker separate from NestJS.
10. Keep Web Admin separate from NestJS.
11. REST API is the primary interface for Flutter and Web Admin.
12. WebSocket is used for real-time updates, not as a replacement for REST.
13. Database schema must support multiple houses, rooms, and devices.
14. Device IDs must be stable and unique.
15. Use environment variables for configuration.
16. Provide .env.example.
17. Never commit secrets.
18. Every important architectural decision should be documented.
19. Do not add infrastructure without a demonstrated need.
20. After every major phase, run tests/build/health checks before proceeding.

===========================================================
11. PHASE 7 - MQTT ARCHITECTURE
===========================================================

Configure NestJS as an MQTT client.

Mosquitto is the broker.

Use a consistent topic convention:

home/{homeId}/{roomId}/{deviceId}/telemetry
home/{homeId}/{roomId}/{deviceId}/state
home/{homeId}/{roomId}/{deviceId}/command
home/{homeId}/{roomId}/{deviceId}/config

Example:

home/home-01/living-room/esp-001/telemetry

ESP publishes telemetry.

NestJS subscribes to telemetry.

NestJS publishes commands.

NestJS should also be able to publish configuration messages.

Do not put business logic directly inside a giant MQTT callback.

Flow:

MQTT message
    |
    v
MQTT service
    |
    v
validate payload
    |
    v
resolve device
    |
    v
telemetry service
    |
    +----> save SensorReading
    |
    +----> update lastSeenAt
    |
    +----> emit WebSocket event

===========================================================
12. MQTT PAYLOAD VALIDATION
===========================================================

Do not assume MQTT payload is valid.

Example telemetry:

{
  "temperature": 28.4,
  "humidity": 72.1
}

Create DTO/schema validation.

Reject malformed payloads.

Handle:

- invalid JSON
- missing fields
- wrong data types
- unknown device
- unknown sensor
- invalid values

Do not crash the MQTT process because one device sends malformed data.

Log errors appropriately.

===========================================================
13. PHASE 8 - SENSOR TELEMETRY
===========================================================

Implement telemetry ingestion.

The initial target is:

- temperature
- humidity

Design the system so additional sensor types can be added later.

Examples:

- pressure
- light
- motion
- air quality
- soil moisture
- energy
- door/window state

Do not create a separate database table for every sensor type.

Prefer a generic sensor + sensor reading model.

Example API:

GET /api/devices/:deviceId/sensors

GET /api/sensors/:sensorId/readings

Support query parameters such as:

?from=
?to=
?limit=

Example:

GET /api/sensors/1/readings?from=2026-08-16T00:00:00Z&to=2026-08-16T12:00:00Z&limit=1000

Do not return unlimited sensor readings.

Always apply reasonable pagination/limits.

===========================================================
14. PHASE 9 - DEVICE ONLINE/OFFLINE STATUS
===========================================================

Implement a simple device presence mechanism.

Whenever telemetry/state is received:

device.lastSeenAt = current time

The API should be able to determine:

ONLINE
OFFLINE

Do not store an unnecessary status row every few seconds.

Use lastSeenAt as the source of truth.

Define a configurable timeout.

Example:

If lastSeenAt is older than 60 seconds:
OFFLINE

The exact timeout should be configurable.

Later, MQTT Last Will and Testament can be added if required.

Do not over-engineer this now.
