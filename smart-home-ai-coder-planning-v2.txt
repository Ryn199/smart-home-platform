SMART HOME PLATFORM - AI CODER DEVELOPMENT PLAN
================================================

PROJECT CONTEXT
---------------

This project is a Smart Home platform for approximately:

- 2 houses
- Multiple rooms
- Less than 10 ESP devices initially
- ESP32-based devices
- MQTT communication
- NestJS + Fastify backend
- PostgreSQL + Prisma
- Separate Web Admin frontend
- Flutter mobile application
- Mosquitto MQTT broker

The project intentionally avoids overengineering.

Do NOT introduce Redis, Kafka, TimescaleDB, Kubernetes, microservices,
or other infrastructure unless explicitly requested later.

The backend is the central authority for:

- authentication
- homes
- rooms
- devices
- device types
- custom sensor telemetry
- specialized device commands
- MQTT communication
- real-time WebSocket updates
- automation

Web Admin and Flutter must communicate with the backend API.
They must NOT communicate directly with MQTT.

================================================
ARCHITECTURAL PRINCIPLE
================================================

The most important architecture rule is:

GENERIC DEVICE MANAGEMENT
        +
DEVICE-SPECIFIC CAPABILITIES
        +
GENERIC CUSTOM SENSOR TELEMETRY

Do NOT force every device into:

Device -> Sensor -> SensorReading

That model is only appropriate for generic/custom sensor devices.

Every physical device is represented by a generic Device entity.

A Device has a DeviceType.

Examples:

CUSTOM_SENSOR
SMART_DOOR
SMART_CURTAIN
EXHAUST_FAN
SMART_LIGHT
SMART_PLUG

The initial implementation should only implement device types actually
needed by the project. The architecture must make it easy to add more later.

------------------------------------------------
GENERIC DEVICE ENTITY
------------------------------------------------

Every physical device must use the generic Device entity.

Suggested generic fields:

- id
- roomId
- name
- deviceUid
- deviceType
- status
- lastSeenAt
- createdAt
- updatedAt

Additional metadata may be added only when useful.

The Device entity is responsible for generic identity and ownership.

It should NOT contain every possible property of every device type.

------------------------------------------------
DEVICE TYPE
------------------------------------------------

Use a controlled type-safe DeviceType.

Initial examples:

CUSTOM_SENSOR
SMART_DOOR
SMART_CURTAIN
EXHAUST_FAN

Future examples:

SMART_LIGHT
SMART_PLUG
THERMOSTAT
AIR_CONDITIONER
WATER_PUMP
IRRIGATION_CONTROLLER
ENERGY_METER

Do not implement future device types unless required.

Do not use arbitrary free-form strings such as:

smartdoor
SmartDoor
SMART_DOOR
door

Use one controlled representation.

An enum is acceptable for the current project.

Do not create a separate database table for every device type unless there is
a concrete domain requirement.

------------------------------------------------
GENERIC DEVICE MODULE
------------------------------------------------

The Devices module should handle only generic device management.

Responsibilities:

- register device
- update device
- delete device
- device UID
- device name
- device type
- room assignment
- generic status
- lastSeenAt
- generic metadata

Do NOT put all specialized behavior inside DevicesService.

Avoid code like:

if SMART_DOOR ...
if SMART_CURTAIN ...
if EXHAUST_FAN ...

throughout the generic DevicesService.

------------------------------------------------

Example:

smart-door/

├── smart-door.controller.ts
├── smart-door.service.ts
├── dto/
└── ...

smart-curtain/

├── smart-curtain.controller.ts
├── smart-curtain.service.ts

└── ...

exhaust-fan/

├── exhaust-fan.controller.ts

The exact structure may be adjusted to match NestJS conventions.

M8 - MQTT BROKER INTEGRATION
================================================

Use Mosquitto as the MQTT broker.

NestJS is an MQTT client/application consumer.

NestJS is NOT the MQTT broker.

Expected communication:

ESP32 <-> Mosquitto <-> NestJS

Suggested topic structure:

home/{homeId}/{roomId}/{deviceUid}/telemetry
home/{homeId}/{roomId}/{deviceUid}/state
home/{homeId}/{roomId}/{deviceUid}/command
home/{homeId}/{roomId}/{deviceUid}/config

Example:

home/home-01/living-room/esp-001/telemetry

Use deviceUid in MQTT topics.

Do not expose MQTT topics directly to Web Admin or Flutter.

NestJS should subscribe to required topics and publish commands.

================================================
M9 - DEVICE-SPECIFIC MQTT ROUTING + MESSAGE HANDLING
================================================

Do NOT create one giant MQTT message callback containing all device logic.

Expected flow:

MQTT message
    |
    v
MQTT service
    |
    v
Resolve device by deviceUid
    |
    v
Resolve deviceType
    |
    +----------------------+-----------------------+
    |                      |                       |
    v                      v                       v
CUSTOM_SENSOR          SMART_DOOR            SMART_CURTAIN
    |                      |                       |
    v                      v                       v
Sensor service        Door service          Curtain service

Other device types follow the same pattern.

Messages must be classified by purpose:

- telemetry
- state
- command
- config

Payloads must be validated.

Malformed MQTT messages must not crash the backend.

------------------------------------------------
CUSTOM SENSOR EXAMPLE
------------------------------------------------

------------------------------------------------
SMART CURTAIN EXAMPLE

------------------------------------------------
EXHAUST FAN EXAMPLE
------------------------------------------------

Specialized modules own their own payload validation and business rules.

M10 - CUSTOM SENSOR TELEMETRY
================================================

Implement generic sensor telemetry.

Only devices that expose generic sensors should use SensorReading.

Example:

Device
 |
 +-- Sensor: temperature
 |      |
 |      +-- SensorReading
 |
 +-- Sensor: humidity
        |
        +-- SensorReading

Implement:

GET /api/devices/:deviceId/sensors

GET /api/sensors/:sensorId/readings

Support query parameters:

from
to
limit

Never return unlimited historical readings.

Use appropriate indexes for:

- sensorId
- recordedAt

For high-frequency sensor data, database queries must always support
reasonable time ranges and limits.

Do NOT add TimescaleDB at this stage.

================================================
M11 - DEVICE ONLINE/OFFLINE STATE
================================================

Use lastSeenAt as the main source of device presence.

Whenever a valid MQTT telemetry or state message is received:

device.lastSeenAt = current time

Determine status using a configurable timeout.

Example:

lastSeenAt older than 60 seconds
=> OFFLINE

Do not create a database row every few seconds just to track online state.

MQTT Last Will and Testament may be added later if useful, but is not
required for the initial implementation.

Clients must NOT provide arbitrary MQTT topics.

DEVICE TYPE ARCHITECTURE RULES
================================================

RULE 1:
Every physical device is represented by the generic Device entity.

RULE 2:
Every Device has a controlled DeviceType.

RULE 3:
Generic device management belongs to the Devices module.

RULE 4:
Specialized behavior belongs to specialized NestJS modules.

RULE 5:
CUSTOM_SENSOR uses Sensor + SensorReading.

RULE 6:
Specialized device state must NOT automatically become SensorReading.

RULE 7:
Specialized commands must be validated by the specialized module.

RULE 8:
MQTT routing resolves the device and delegates based on DeviceType.

RULE 9:
Do not create a database table for every device type without a concrete
requirement.

RULE 10:
Do not put all device-specific behavior inside DevicesService.

RULE 11:
Automation calls device services rather than constructing raw MQTT topics.

RULE 12:
Web Admin and Flutter communicate with backend APIs, not directly with MQTT.

RULE 13:
MQTT topic structure remains consistent across device types.

RULE 14:
Device-specific payloads may differ but must be validated and documented.

RULE 15:
Adding a new device type should preferably require a focused module rather
than changes throughout the entire codebase.
